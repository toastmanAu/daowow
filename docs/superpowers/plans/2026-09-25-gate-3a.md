# Gate 3a Implementation Plan — freeze and aggregate into the DAO

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Drive a filled round from OPEN through FROZEN, ledger genesis, and one
or more accepted batches, each batch producing a native Nervos DAO deposit.

**Architecture:** Pure JavaScript builders that emit unsigned transactions in
ckb-cli's tx-file format, plus a checker that re-derives every on-chain rule
from the finished bytes before Phill signs. No process ever holds a key. The
codecs are ported from `daowow-core` and pinned byte-for-byte to
Rust-generated vectors.

**Tech Stack:** Node (no build step), the vendored CCC bundle for hashing and
molecule, `node:test`, `ckb-cli` for signing, Rust `gen_vectors` for oracles.

**Spec:** `docs/superpowers/specs/2026-09-24-gate-3a-design.md`

## Global Constraints

- **Three transactions, not fewer.** Freeze, genesis and batch are separated by
  contract rules, not by taste: `AggregationState::new_bound` (`lifecycle.rs:99`)
  refuses an input shard whose `state` is not already `FROZEN`, and
  `no_entry_inputs` (`ledger.rs:26`) forbids entry cells in the genesis. Do not
  attempt to merge them.
- **No key material.** Builders emit unsigned transactions. Phill signs with
  ckb-cli. Nothing in this repository reads, stores or logs a private key.
- **ckb-cli tx-file format**, `{transaction, multisig_configs, signatures}`.
  Never instruct anyone to run `ckb-cli tx init` on a prepared file — it writes
  an empty skeleton over it.
- **Every input's lock needs a cell dep.** Use `tools/lock-deps.mjs`.
  `dep_group` is preferred over a bare code cell.
- **Ported rules are pinned to their Rust line.** Every function ported from
  `daowow-core` cites the file and line it came from and is tested against a
  Rust-generated vector, never against our own output.
- **A guard is not pinned until a mutation reds its own named test, alone.**
  Run the disable/re-enable round trip per guard, never for a set.
- `--skip-check` is required on `ckb-cli tx send` for any transaction carrying
  a public-lock cell; ckb-cli cannot classify that lock and refuses it.
- Commit messages end with `Co-Authored-By: Claude Opus 5 (1M context) <noreply@anthropic.com>`.

### Task 5: The ledger genesis transaction

**Files:**
- Create: `apps/web/chain/genesis-tx.js`
- Test: `apps/web/test/genesis-tx.test.js`

**Interfaces:**
- Consumes: `ledger-codec.js`, `codec.js`, `quote.js` for capacity arithmetic.
- Produces: `buildLedgerGenesisTx({manifest, config, frozenShard,
  configCellOutPoint, sponsor}) -> {tx, expectedLedger, topUp}`.

The input is the FROZEN shard; the output is the 207-byte ledger under the same
type args and a public lock. The client computes `AggregationState::new`
locally so it can be checked, but the contract recomputes it — so a wrong
value is refused, not accepted.

**The capacity is the interesting part.** The shard cell occupies
8 + 101 + 34 + 69 = 212 CKB; the ledger occupies 8 + 207 + 34 + 69 = **318 CKB**.
The demo shard carries 312, so genesis is **6 CKB below its own floor** while
`ledger.rs:54` separately demands `out_cap >= in_cap`. Compute both bounds and
take the larger; never assume the shard's capacity carries over.

- [ ] **Step 1: Write the failing tests**

```js
test("the ledger cell clears its own floor and the input's capacity", () => {
  const { tx, topUp } = buildLedgerGenesisTx({ ...base });
  const cap = BigInt(tx.outputs[0].capacity);
  assert.ok(cap >= 318n * CKB, "below the 318 CKB occupied floor");
  assert.ok(cap >= BigInt(frozenShard.capacity), "below the input's capacity");
  assert.ok(topUp > 0n, "the demo shard's 312 CKB cannot cover 318");
});

test("the genesis state matches what the contract will recompute", () => {
  const { tx } = buildLedgerGenesisTx({ ...base });
  const state = decodeAggregationState(unhex(tx.outputsData[0]));
  assert.strictEqual(state.acceptedEntries, 0n);
  assert.strictEqual(state.acceptedBatches, 0n);
  assert.strictEqual(state.closed, false);
  assert.deepStrictEqual(state.frozen, frozenShard);
});

test("an OPEN shard is refused: genesis needs state FROZEN", () => {
  // lifecycle.rs:99. The dispatch routes on data length alone, so this
  // transaction WOULD be built and WOULD be refused on chain as
  // SHARD_ERROR_STATE, which says nothing about the cause.
  assert.throws(() => buildLedgerGenesisTx({
    ...base, frozenShard: { ...frozenShard, state: 0 },

});

test("an entry cell in the genesis is refused: no_entry_inputs", () => {
```

### Task 6: The aggregate transaction

The largest task. Split the pure batch arithmetic from transaction assembly so
the arithmetic is testable without a chain.

**Files:**
- Create: `apps/web/chain/aggregate-tx.js`
- Test: `apps/web/test/aggregate-tx.test.js`

**Interfaces:**
- Consumes: `ledger-codec.js`, `ledger-witness.js`, `entry-codec.js`,
  `../core.js` (`MmrHost.membershipProof`), `lock-deps` shapes.
- Produces: `acceptBatch(config, state, entries, capacities) -> {next, batch}`
  (pure, mirrors `AggregationState::accept`), and
  `buildAggregateTx({manifest, config, ledger, entryCells, allEntries,
  configCellOutPoint, sponsor}) -> {tx, expectedLedgerAfter, batch, batchId}`.

Three outputs, all required (`ledger.rs`, `validate_aggregation`):

1. ledger successor — same type args, public lock, `next.encode()`, `cap >= in_cap`
2. DAO deposit — lock `dao_lock` with args `round_id ‖ batchId LE ‖ commitment ‖
   digest` (104 bytes), type the config's `dao_type`, data eight zero bytes,
   capacity **exactly** `batch.inputCapacity`
3. receipt — type entry-shard-type with 77-byte args
   `2 ‖ commitment ‖ shardId ‖ batchId ‖ digest`, public lock, empty data

The witness sits at the **ledger input's index** and carries
`{inputIndex, proof}` per entry.

```js
  assert.strictEqual(hex(encodeAggregationState(next)),

});

test("more than 32 entries in one batch is refused", () => {
```
