## What exists on chain now

**Claim cell** (one per ticket, minted inside the entry append transaction)

- lock: the holder's wallet lock
- type: `entry-shard-type` code hash, args `[5] ‖ config_commitment(32) ‖ shard_id(u32 LE) ‖ position(u64 LE)` (45 bytes)
- data: `PrizeRedemptionState` (81 bytes): version 1, ticket id, paid-set SMT root, paid count, paid total
- occupied capacity: 200 CKB with an argless lock, 220 CKB with secp256k1; returned at retirement (sub-project 3)

**Claim script modes** (`contracts/entry-shard-type/src/claim.rs`)

- mint: no group input; requires an OPEN shard of the same identity as input and output (the shard append counts claims: exactly one per new ticket, locked to the entrant, fresh state)
- transfer: one in, one out, byte-identical data, any lock
- redeem: data differs; exactly one settlement funding input of this commitment must name this claim in its redemption witness; output state must equal `record_verified_prize(prize_source, amount, absence_proof)`; lock unchanged
- retire (input, no output): authenticated against the sealed round from cell
  deps alone — a config cell (commitment-matched), the canonical entropy
  record (`commitment ‖ 0u32` identity, version-4 data), and the round's own
  committed prize schedule supplied raw at the retiring claim's group-input
  witness (checked against `cfg.prize_schedule_hash`). `retire_decision`
  re-derives the real `ComputedDraw` and requires `paid_count == 0` for a
  ticket never drawn (immediate retirement once the round is sealed) or
  `paid_count == total_accepted_batches()` for a drawn ticket (every prize
  obligation discharged). A non-winner mints no memento; a winner must mint
  exactly one, under its own holder lock, at its own identity
  (`entry-shard-type` mode `[6]`)

**Memento cell** (minted only alongside a retiring winning claim)

- lock: the retiring claim's own holder lock (checked by the claim script)
- type: `entry-shard-type` code hash, args `[6] ‖ commitment(32) ‖ shard_id(u32 LE) ‖ position(u64 LE)` (45 bytes, `MEMENTO_ARGS_SIZE`)
- data: `MementoData` (54 bytes, `MEMENTO_DATA_SIZE`): renderer tag, renderer
  version, the committed `WINNER_TEMPLATE_SHA256` artwork hash, prize (draw
  rank) index, paid count, paid total — every field authenticated by the
  retiring claim's own script, not by the memento script itself
- non-financial: carries no prize rights and authorizes nothing
  (`contracts/entry-shard-type/src/memento.rs`)

**Memento script modes** (`contracts/entry-shard-type/src/memento.rs`)

- mint: no group input; requires exactly one claim of this identity as input
  and none as output (the retiring claim, whose script has already
  authenticated every field of this mint)
- transfer: one in, one out, byte-identical data, any lock — non-financial,
  so ownership carries no additional check
- burn (input, no output): always allowed; nothing to discharge

**Funding cell v3** (`SettlementFundingDataV3`, 160 bytes): the eight V2 fields
plus `prize_count`, `prize_root` (MMR over `prize_leaf(ticket, amount)` sorted
by ticket id) and `prize_paid`. Created by DAO phase two exactly as before, but
`InitialEntitlements::derive` now credits prizes to ticket ids and principal
only to depositors. Winner ownership proofs no longer exist; the phase-two
witness is version 2.

**Settlement modes** (`contracts/settlement-type/src/main.rs`)

- payout (witness first byte is a count): unchanged principal path, except a
  non-final payout may now reach the last liability while prizes are
  outstanding, and a final drain requires prizes complete
- redemption (witness first byte `0xFF`): up to 32 items, each proving
  `prize_leaf(ticket_from_claim_args, amount)` at `prize_index`, paying the
  claim's current lock, requiring the claim successor's counters to advance by
  exactly that item; `prize_paid` grows by the sum; conservation as for payouts
- final drain on either path: `payout_cursor == liability_count` and
  (`prize_count == 0` or `prize_paid == prize_pool`)

**Error codes** (`crates/daowow-core/src/error.rs`): `SHARD_ERROR_CLAIM_CELL -38`,
`SETTLE_ERROR_REDEEM -77`, `CLAIM_ERROR_ARGS -91`, `_DATA -92`, `_GROUP -93`,
`_MINT -94`, `_TRANSITION -95`, `_RETIRE -96`, `_REDEEM -97`,
`CLAIM_ERROR_UNIVERSE -98` (sealed round / entropy record / config could not
be authenticated from cell deps, or the committed schedule witness did not
decode), `CLAIM_ERROR_INCOMPLETE -99` (a drawn ticket retiring before its
`paid_count` reaches the round's `total_accepted_batches()`),
`MEMENTO_ERROR_ARGS -100`, `MEMENTO_ERROR_DATA -101`, `MEMENTO_ERROR_GROUP
-102`, `MEMENTO_ERROR_MINT -103`.

**Pure core** (`crates/daowow-core/src/`): `claim.rs` (args, initial state,
`validate_mint`, `validate_transfer`, `claim_occupied_capacity`),
`redemption.rs` (`prize_source`, obligation key, payment leaf,
`PrizeRedemptionState`), `leaf.rs::prize_leaf`, `computed_draw.rs::locate`,
`entitlements.rs` (`PrizeEntitlement`, `prizes()`), `witness.rs`
(`RedemptionItem`, `encode/decode_redemption_witness`,
`MAX_REDEMPTION_ITEMS = 32`, `MAX_REDEMPTION_WITNESS_BYTES = 128 KiB`),
`claim.rs::retire_decision` (`RetireDecision::{NonWinner, Winner}`, the
count-based obligation-universe test), `memento.rs` (`MementoArgs`,
`MementoData`, `memento_occupied_capacity`, `WINNER_TEMPLATE_SHA256`).

**Viability gate** (`computed_draw.rs::MAX_POOL_BAR`, 0.01 CKB /
1,000,000 shannons): `ComputedDraw::new` only draws positions when the
accepted universe is nonempty, meets `cfg.minimum_tickets`, and the
schedule's `min_viable_pool(total)` stays at or below this bar. A round that
fails this gate produces **no** drawn positions at all — every claim in that
round is a non-winner (`retire_decision` returns `NonWinner` for every
ticket, since none appear in `draw.positions()`) and retires immediately
once the round is sealed, with no memento minted by anyone. This is the
deliberate "failed round" path: the same evidence chain (config + entropy
record + committed schedule) that lets a winner retire also lets every
holder in an unviable round recover their claim's capacity, with no special
case in the claim script for "the round failed" versus "I personally didn't
win."

```bash

for c in round-type entry-shard-type entry-lock dao-lock settlement-type accumulator-bench smoke-alloc smoke-minimal; do
  cargo build --target riscv64imac-unknown-none-elf --release -p $c
done
cargo test -p daowow-core --lib                          # 148 tests
cargo check -p daowow-core --no-default-features         # no_std
cargo clippy -p daowow-core --lib -- -D warnings
cargo test -p daowow-core --test gen_vectors             # rewrites tests/vectors/daowow_core_vectors.json

```

## Traps learned the hard way (all recorded in `~/.claude/rules/ckb-transactions.feedback.md`)

- `ckb-testtool`: never re-verify a transaction after `chain_cell` advanced its
  input; the script sees before == after. Return cycles from the helper.
- CKB executes script groups in script-hash order, not input order. When two
  scripts both reject, the reported code is hash luck. To pin a guard in
  script A, keep script B consistent (recompute its expected state).
- A rejection test that pairs a forged cell with garbage decoy data pins
  nothing; use a decodably valid decoy so only the guard under test can refuse.
  Then prove it by mutation: remove the guard, the named test must go red.
- Occupied capacity of a script is `33 + args.len()`, not the molecule
  `as_slice().len()` (which carries a 16 to 20 byte header).
- Cell floors bind transaction order: a funding successor must keep about
  307 CKB and a payment cell 47 to 61 CKB. Small prize pools must be redeemed
  before the principal drain, and sub-floor prizes need a sponsor top-up the
  contract tolerates but does not count.
- Wire bounds must be checked jointly against the 512 KiB never-freed script
  heap; per-field caps alone let a valid witness abort the VM.
- Two-script validation splits need the paying script to verify the
  counterparty's state advanced by exactly the item, not merely that a
  successor exists (an unchanged successor passed the claim script as a
  transfer while the settlement paid).
- Do not rebuild contract binaries while the devnet suite runs; each test
  deploys the binaries fresh.

## Sub-project 3: retirement and winner memento (done)

Implemented as designed: retirement is a claim-only transaction authenticated
purely from cell deps (config + canonical entropy record) plus the round's
committed prize schedule supplied raw at the retiring claim's own witness —
no need to ride the last redemption. The memento is a new mode of
`entry-shard-type` (`[6]`, alongside claim's `[5]`), not a separate script,
consistent with the claim's own identity scheme. Its data layout commits to
the renderer version, the fixed `WINNER_TEMPLATE_SHA256` artwork hash, the
draw's prize (rank) index, and the claim's paid count/total — no separate
render seed; the ticket id is recoverable from the shared `commitment ‖
shard_id ‖ position` args rather than duplicated into the data.

The obligation-universe test resolved to a plain count comparison rather than
per-source membership proofs: `retire_decision` (`crates/daowow-core/src/claim.rs`)
requires `paid_count() == total_accepted_batches()` for a drawn ticket, or
`paid_count() == 0` for one never drawn. This is sound because every recorded
source was itself verified against a real funding cell under an absence
proof before being counted (see `redemption.rs`), so sources are guaranteed
genuine and distinct — a count match is equivalent to a full membership
check without re-walking the paid set. Failed (unviable) rounds fall out of
the same mechanism for free: see "Viability gate" above.

Full detail: `docs/superpowers/specs/2026-09-16-claim-retirement-memento-design.md`
(design), `docs/superpowers/plans/2026-09-16-claim-retirement-memento.md`
(the eleven implementation tasks, this devnet proof being the last),
`docs/results/2026-09-16-retirement-memento-results.md` (mutation-probe table
and the full-gate/devnet proof).

## Other open items

- Unclaimed prizes leave a funding cell open indefinitely (decided for the
  beta); an expiry sweep would need a config field and a since-gated mode.
- `entry-shard-type` scans all outputs twice per append (claim collection and
  entry matching) and the settlement's successor search is O(items x outputs);
  a single-pass scan is a cost follow-up, not a correctness issue.
- The web entry quote does not show claim capacity yet
  (`claim_occupied_capacity(33 + lock_args_len)`); `apps/web/engine.js` still
  simulates prizes paid to participants.
- `beta-rule-enforcement-audit.md` items (round-wide cap, per-lock cap, entry
  opening/closing enforcement) are unchanged by this work.
- Deployment manifest is still `prototype-code-cells-only`; the testnet code
  cells predate all of this and must be redeployed before any funded round.
- `tests/integration/tests/security_redemption.rs::redeeming_the_same_source_twice_is_rejected_by_the_claim`
  is a real, pre-existing defect independent of this work: it was reported to
  this task as a known failure (a host-side `in_cap - amount` underflow in
  the test's own setup) said to reproduce on `main`. On this run it passed —
  deterministically, in isolation and inside the full suite — and the file
  has not changed since it was last touched
  (`4461d8b feat: authenticate claim retirement against the sealed round`).
  This is recorded as an open discrepancy to resolve, not silently corrected:
  either the failure is no longer reproducible and the "known failures" list
  is stale, or it is timing/environment-sensitive and this run got lucky.
  Whoever picks this up next should re-run it a few times before trusting
  either conclusion, and should not assume this task fixed anything in that
  file (it did not touch it).
- Retire-path cost at the maximum shard count is MEASURED and fits. A
  non-winner retire against a 256-shard sealed round (the configured maximum,
  ~53 KB of `AggregationState`) completes in 7,014,088 cycles with no heap
  abort, against roughly 685k-760k cycles at 4 shards. The concern was that
  retire() decodes and re-encodes the whole seal on the 512 KiB bump allocator
  that never frees, and that exhausting it would make every claim in that round
  permanently unretirable. It does not. Pinned by
  `claim_retirement.rs::a_non_winner_retires_at_the_maximum_shard_count`. The
  available optimisation — `ComputedDraw::new` re-encodes a record the caller
  already holds as bytes, worth roughly 106 KB of peak — is therefore NOT
  needed, and was deliberately not taken: it would require passing the encoding
  alongside the record, which is a footgun in a consensus-critical path for no
  measured benefit.
- `MAX_POOL_BAR`'s margin arithmetic is CORRECTED. The bar is 45.5 parts per
  million of a 220 CKB minimum ticket, not one part per million, and the margin
  over a full term is about 54x, not 20x. Both figures are fixed in the
  constant's doc comment and the design spec. No config floor is needed: the
  review inferred the margin fails for short terms, but there are none —
  `dao_term_periods` counts 180-epoch DAO cycles (`epoch.rs` targets
  `deposit + periods * 180`, enforced on chain by dao-lock) and `validate()`
  requires at least one, so the minimum enforceable term is a full cycle. A
  single-epoch batch would yield ~3x10^5 shannons and fall under the bar, but
  no such term can be constructed.
- Conflated error causes are SPLIT. `retire_decision` now returns
  `CoreError::Impossible` (mapped to `CLAIM_ERROR_IMPOSSIBLE`, -104) for a
  non-winner carrying discharged sources, distinct from the
  `StateTransition`/`CLAIM_ERROR_INCOMPLETE` a winner gets for retiring before
  collecting everything — one says investigate, the other says try again.
  `derive()` returns `InvalidArgument` for a genuinely zero-yield batch,
  distinct from the `Conservation` an allocation failure returns; both strand
  the batch permanently, so the cause matters. Pinned on chain by
  `security_retirement::a_non_winner_carrying_payments_is_reported_as_impossible`.
- Integration fixtures are binary-hash-fragile: the harness bakes each
  deployed binary's data hash into `RoundConfigV1`, so `cfg.commitment()` and
  therefore the draw seed depend on the contract binaries' exact bytes. Any
  contract change reshuffles which tickets win in every fixture. Prefer
  deriving expected amounts from the draw itself rather than pinning
  `ScriptRef`s.
- If the protocol ever moves from `data1` to Type ID deployment, the
  viability gate becomes retroactive: a redeployed binary could re-evaluate
  an already-drawn round as void, turning winners who had already redeemed
  into non-winners with `paid_count != 0` — permanently unretirable. Needs
  one explicit sentence of warning in the deployment manifest before that
  move is made.
